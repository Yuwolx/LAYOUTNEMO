## 1. 업그레이드 대신 삭제

아침 보안 업그레이드 때 남겨 둔 숙제가 있었다: `ai`(Vercel AI SDK) 패키지의 취약점은 수정판이 ai@7 메이저라, "AI 기능 전체 재검증이 필요한 큰 건"으로 분류해 뒀었다. 오늘 그걸 착수하면서 첫 단계로 사용처를 훑었는데 —

```
// grep 결과: 소스 어디에도 없다
from "ai"        → 0건
@ai-sdk          → 0건
```

AI 생성·정리하기 라우트는 전부 **OpenAI 를 raw fetch 로 직접 호출**하고 있었다. `ai` 패키지는 초기에 깔아만 두고 한 번도 쓰지 않은 채 취약점 경고만 만들고 있던 것. `npm uninstall ai` 한 줄로 "큰 건"이 끝났고, audit 에 남은 건 next 가 내부에 고정해 둔 postcss(중간 심각도, next 패치 대기)뿐이다.

교훈이 하나 있다면: **취약점 대응의 첫 질문은 "어떻게 올리지"가 아니라 "진짜 쓰고 있나"다.** 계획을 세울 때 심각도와 수정 버전만 보고 사용처 확인을 건너뛰었다 — 확인했다면 아침에 이미 지웠을 것이다.

## 2. 정리하기가 기한을 못 보고 있었다

로드맵의 "정리하기 AI 입력에 태그/기한 포함"도 열어 봤다. 태그는 알고 보니 코드에 존재하지 않는 필드였고(과거 계획의 잔재), **기한은 존재하는데 배선이 끊겨 있었다**:

```
// 서버 프롬프트: 기한을 출력할 준비가 되어 있다
`기한: ${b.dueDate || "없음"}`
// 클라이언트: dueDate 를 안 보낸다 → 항상 "없음"
blocks.map((b) => ({ id, title, zone, urgency, x, y, ... }))  // dueDate 없음
```

프롬프트에는 심지어 "기한 임박인데 상태가 시급이 아닌 경우"라는 제안 카테고리까지 정의돼 있었다. 재료가 안 들어오니 **그 카테고리는 태어나서 한 번도 발동한 적이 없는** 셈이다. 게다가 오늘 날짜도 프롬프트에 없어서, 기한이 들어갔더라도 "임박"을 판단할 기준이 없었다.

```
// 해결: 클라이언트가 dueDate 를 보내고, 프롬프트에 {TODAY} 기준일 추가
dueDate: b.dueDate || null
"오늘 날짜: {TODAY} (기한 임박 여부는 이 날짜 기준으로 판단)"
```

이제 정리하기가 "이 블럭 기한이 모레인데 아직 미정이네요, 시급으로 바꿀까요?" 같은 제안을 할 수 있는 조건이 갖춰졌다.

## 정리

- **취약점 목록의 패키지가 정말 쓰이는지부터 grep 하라.** "메이저 업그레이드 필요"라고 적어 둔 계획이 사실은 `npm uninstall` 한 줄이었다.
- **프롬프트의 능력은 프롬프트 텍스트가 아니라 입력 배선이 정한다.** "기한 임박" 카테고리는 완벽하게 정의돼 있었지만, 데이터가 안 들어와 영원히 침묵했다. AI 기능을 점검할 땐 프롬프트만 읽지 말고 실제로 뭐가 들어가는지를 봐야 한다.
- 로드맵 항목은 몇 달 지나면 현실과 어긋난다("태그"는 존재하지 않았다). 착수 전 검증이 계획 수정보다 싸다.

롤백 지점은 `release/pre-ai-dep-cleanup`. 기한 기반 제안의 품질은 라이브에서 실제 정리하기를 돌려 봐야 안다.
