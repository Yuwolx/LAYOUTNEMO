## 무슨 일이 있었나

터치 지원(7/2)과 헤더 정리(오늘 오전)가 실기기에서 확인됐다. 태블릿 사용자가 다음으로 기대하는 건 자명했다: **핀치 줌**. 그리고 휴대폰은 화면이 좁아 기본 배율 90%로는 캔버스가 답답했다.

줌은 이 프로젝트에서 사연이 있는 기능이다. 초기에 넣었다가 좌표 변환 비용 때문에 뺀 적이 있다. 그런데 그 사이 사정이 바뀌었다 — 기본 배율 90%를 도입하면서 **모든 좌표 변환이 이미 `screen = pan + world × scale` 한 공식으로 정리**되어 있었다. 상수 `DEFAULT_CANVAS_SCALE`이 드래그·마퀴·갈무리 드롭·검색 이동·새 블럭 배치까지 전부 관통하고 있었으니, 줌은 "그 상수를 상태로 바꾸는 일"이 됐다.

## 1. 상수를 상태로

```
// 문제: 배율이 컴파일 타임 상수 — 줌 불가능
const DEFAULT_CANVAS_SCALE = 0.9
// 해결: 상태로. 좌표 변환 9곳의 상수 참조를 전부 state 로 교체
const [scale, setScale] = useState(DEFAULT_CANVAS_SCALE)
```

말은 한 줄인데 실수하면 무서운 작업이다. 한 곳이라도 상수를 남기면 **줌 상태에서 그 기능만 좌표가 어긋난다** — 드래그하면 블럭이 손가락에서 미끄러지고, 마퀴는 엉뚱한 블럭을 잡는다. 교체 후 `DEFAULT_CANVAS_SCALE` 잔존 참조를 grep 으로 확인하는 것까지가 작업이었다.

## 2. 두 번째 손가락이 서 있을 자리

진짜 문제는 좌표가 아니라 **이벤트 구조**였다. 터치 지원 때 멀티터치 가드를 이렇게 만들었다:

```
// 기존: 한 번에 하나의 인터랙션만 — 두 번째 손가락은 무시
if (activePointerIdRef.current !== null) return
```

이 가드는 "두 손가락으로 서로 다른 블럭을 동시에 끌면 캔버스가 찢어지는" 사고를 막는 핵심인데, 핀치는 정확히 **두 번째 손가락이 필요한** 제스처다. 가드를 풀 수는 없다. 답은 가드 앞단에서 감지하는 것:

```
// 해결: window 캡처 단계에서 터치 포인터를 전부 추적 —
// 기존 핸들러(버블 단계)가 두 번째 손가락을 버리기 전에 핀치를 판정한다
window.addEventListener("pointerdown", handleDown, true /* capture */)
```

두 손가락이 모이면 진행 중이던 팬/마퀴를 정리하고 핀치로 전환한다. 손가락 중심점 아래 있던 월드 지점을 기억해 두고, 이동할 때마다 그 지점이 계속 중심 아래 오도록 pan 을 보정한다 — 그래서 벌리면 **손가락 사이가** 커지고, 두 손가락을 같이 끌면 팬도 된다. 한 손가락을 떼면 남은 손가락으로 팬이 이어진다.

결정 하나: **블럭을 드래그하는 중에 두 번째 손가락이 닿으면 핀치로 전환하지 않는다.** 드래그는 명시적 의도라, 실수로 닿은 손가락이 그걸 끊는 것보다 낫다.

## 3. 데스크톱도 같이

트랙패드 핀치는 브라우저가 `ctrlKey + wheel` 로 전달한다. 즉 휠 핸들러 하나면 데스크톱 줌이 공짜다.

```
// Ctrl(⌘)+휠 = 커서 기준 줌 / 그냥 휠 = 캔버스 팬
// 브라우저 페이지 줌을 막아야 하므로 React onWheel(passive) 대신 native non-passive
el.addEventListener("wheel", handleWheel, { passive: false })
```

부수 효과로 마우스 휠/트랙패드 스크롤 캔버스 팬도 생겼다 — Figma·Miro 에서 익숙한 그 감각이다. 그리고 이게 **로컬에서 줌 좌표 변환을 검증할 수 있는 유일한 경로**이기도 했다. 핀치는 실기기가 필요하지만 수식은 같으니까.

## 4. 휴대폰 몫

- 640px 미만은 기본 배율 60% — 좁은 화면에 더 넓은 캔버스가 담긴다.
- 배율이 기기 기본값에서 벗어나면 좌하단에 `120% ↺` 배지가 떠서, 탭 한 번에 화면 중앙을 유지한 채 복귀.

덤으로 아침에 나온 질문("태블릿인지 어떻게 알고 선택 버튼이 뜨나")에서 발견한 구멍도 같이 실었다: 선택 모드 버튼이 `hover: none`(주 입력 기준) 판정이라 **태블릿에 마우스만 연결하면(키보드 없음) 버튼이 사라지는데 Ctrl 도 없어 멀티 선택 수단이 전무**해졌다. `any-pointer: coarse`(터치스크린 존재 여부)로 바꿔 마우스를 붙여도 버튼이 남는다. 블럭 ⋮ 어포던스도 동일하게.

## 정리

- **기능을 "뺐다"는 결정은 영원하지 않다.** 그때 비쌌던 이유(흩어진 좌표 변환)가 다른 작업(기본 배율 도입)으로 해소되면, 다시 넣는 비용은 급락한다.
- **가드를 풀지 말고 가드 앞단에서 잡아라.** 멀티터치 가드는 여전히 유효하다. 핀치는 그 가드가 보기 전(캡처 단계)에 두 손가락을 가로챈다.
- **줌의 좌표 보정은 "고정하고 싶은 월드 지점" 하나로 정리된다.** 손가락 중심이든 커서든 화면 중앙이든, `pan = 화면점 - 월드점 × 새배율` 한 공식.
- **기기 판정은 UA 추측이 아니라 능력(capability) 질의로.** `hover`/`any-pointer` 미디어쿼리는 브라우저가 실제 입력장치 기준으로 답한다. 단, "주 입력"과 "아무 입력"의 차이가 오늘 같은 구멍을 만든다.

롤백 지점은 `release/pre-pinch-zoom`. 핀치 감각·줌 상태 드래그 정확도는 실기기 확인이 남아 있다.
