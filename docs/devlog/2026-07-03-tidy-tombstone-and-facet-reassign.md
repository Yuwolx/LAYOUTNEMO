## 무슨 일이 있었나

로드맵에 "정리하기 적용 시 삭제 블럭 보존/히스토리 처리 강화"라고 적어 뒀었다. 막연히 "더 안전하게 다듬자" 정도로 생각했는데, 코드를 열어 보니 다듬을 문제가 아니라 **이미 터져 있는 문제**였다.

정리하기(AI 제안) 다이얼로그의 배선이 이랬다.

```
// 문제: 다이얼로그는 삭제 블럭을 뺀 목록을 받고,
//       수락 시 그 목록으로 캔버스 전체를 교체한다
<ReflectionDialog blocks={activeBlocks} onUpdateBlocks={setBlocks} />
```

`activeBlocks`는 soft-delete(`isDeleted`)된 블럭을 걸러낸 목록이다. 그런데 제안을 수락하면 그 걸러진 목록에 변경을 얹어 **캔버스 blocks 전체를 교체**했다. 결과: [6월 29일에 만든](2026-06-29-sync-pruning-fix.md) 동기화용 삭제 마커(tombstone)가 로컬 상태에서 전부 증발한다. 삭제 마커가 사라지면 다른 기기와 병합할 때 **지운 블럭이 되살아날 수 있다**. 정리하려고 누른 버튼이 유실 경로였던 셈이다.

덤으로 두 가지가 더 있었다.

- 수락이 히스토리를 우회하는 raw setter로 들어가서 **Ctrl+Z로 되돌릴 수 없었다.** AI가 바꾼 건데 실행 취소가 안 되는 건 최악의 조합이다.
- 적용 로직의 `else` 분기가 **AI가 말한 필드를 뭐든 그대로 덮어썼다.** 프롬프트는 x/y/relatedTo/zone/urgency만 제안하라고 하지만, 응답이 `isDeleted`를 들고 와도 막을 방법이 없었다.

## 어떻게 풀었나 — 전체 교체 대신 변경분 병합

다이얼로그가 "새 blocks 배열"을 만들어 내려보내는 구조 자체가 문제였다. 걸러진 목록을 쥔 쪽이 전체를 교체하면 안 보이는 것들이 같이 죽는다. 그래서 계약을 바꿨다: 다이얼로그는 **변경분(블럭 id + 바뀐 필드)만** 내보내고, 병합은 전체 목록을 쥔 부모가 한다.

```
// 해결: 변경분만 올려보내고, 부모의 기존 배치 업데이트 경로를 재사용
onApplyChanges={handleBatchUpdateBlocks}
// → 전체 목록 기준 id 병합이라 tombstone 보존
// → 수락 1회 = 히스토리 스냅샷 1개 → Undo 가능
```

`handleBatchUpdateBlocks`는 드래그 멀티선택 때 만들어 둔 함수다. 전체 blocks를 순회하며 해당 id만 갱신하니 tombstone은 건드리지 않고, `saveToHistory`를 타니 Undo도 된다. 새 코드를 짠 게 아니라 이미 안전한 경로에 태웠다.

적용 필드도 화이트리스트로 잠갔다. AI 응답이 뭐라 하든 x/y/relatedTo/zone/urgency만, 그것도 값 검증(숫자 유한성, 존재하는 결/블럭 id, 4단계 상태값)을 통과해야 적용된다.

## 결 삭제 — "어디로 옮길까요?"

이어서 로드맵의 다음 항목. 결(facet)을 삭제하면 그 결의 블럭은 일괄 "미분류"가 됐다(FK 사망 버그를 잡으며 넣은 동작). 동작은 맞는데, 블럭이 20개 있는 결을 지울 때 전부 미분류로 흩어지는 건 사용자 입장에선 정리가 아니라 해체다.

결 관리 다이얼로그의 삭제 버튼을 눌렀을 때, 블럭이 있으면 인라인으로 한 단계를 끼웠다.

```
'디자인' 결에 블럭 12개가 있어요. 블럭을 어디로 옮길까요?
[미분류 (결 없음)] [개발] [기획] [마케팅]
[옮기고 삭제] [취소]
```

선택지는 블럭 상세와 같은 칩 버튼 — 셀렉트박스보다 태블릿 터치에 낫다. 빈 결은 그대로 confirm 한 번으로 지워진다.

재배정은 tombstone을 포함한 **전체 블럭**에 적용한다. 화면에 안 보이는 삭제 블럭도 죽은 zone_id를 물고 있으면 autosave가 FK 위반으로 죽기 때문이다.

## Undo가 죽은 결을 부활시키는 구멍

이 작업을 하다 하나 더 발견했다. 히스토리 스냅샷은 blocks만 저장하고 zones는 저장하지 않는다. 그래서 **결 삭제 전에 찍힌 스냅샷으로 Undo**하면, 블럭들이 이미 지워진 zone_id를 다시 물게 된다 — 7월 3일 아침에 잡은 FK 사망 버그가 Undo 경로로 되돌아오는 것이다.

```
// 해결: 스냅샷 적용 시 현재 존재하지 않는 결 참조는 미분류로 비운다
const validZoneIds = new Set(c.zones.map((z) => z.id))
snap.blocks.map((b) => (b.zone && !validZoneIds.has(b.zone) ? { ...b, zone: "" } : b))
```

## 정리

- **걸러진 목록으로 전체를 교체하면, 걸러진 것들이 같이 죽는다.** 필터된 뷰를 받은 컴포넌트에는 전체 교체 권한을 주지 말 것. 변경분만 올려보내고 병합은 원본을 쥔 쪽이.
- **AI가 적용하는 변경일수록 Undo가 있어야 한다.** 사용자가 직접 한 게 아니니까 더더욱.
- **AI 응답은 스키마를 믿지 말고 적용 지점에서 화이트리스트로.** 프롬프트가 금지해도 응답은 뭐든 들고 올 수 있다.
- **참조 무결성은 정방향(삭제)만이 아니라 역방향(Undo)에서도 깨진다.** 스냅샷을 되살릴 때도 현재 상태와의 정합을 검사해야 한다.

롤백 지점은 `release/pre-tidy-zone-ux`. 정리하기 수락 → Undo, 결 삭제 → 재배정 흐름은 라이브에서 확인이 필요하다(로컬은 Supabase 미설정이라 동기화 경로가 안 돈다).
