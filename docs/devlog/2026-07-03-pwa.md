## 무슨 일이 있었나

핀치 줌까지 붙고 나니 자연스러운 질문이 나왔다 — **이거 앱으로 만들면?** 선택지를 정리해 보면: ① PWA(웹앱 그대로, 홈 화면 설치) ② Capacitor(웹뷰 래핑, 스토어 입점) ③ React Native(재작성). ③은 오늘까지 다듬은 캔버스 터치 감각을 처음부터 다시 만드는 일이라 논외. ②는 스토어가 목표가 될 때. **①은 코드 재사용 100%에 하루 거리**라 바로 했다.

LAYOUTNEMO 는 PWA 와 궁합이 유난히 좋은 조건이었다: 로컬 우선(오프라인에서 원래 동작), 터치 최적화 완료(Pointer Events·핀치 줌), HTTPS(Vercel). 필요한 건 매니페스트·아이콘·서비스워커 세 가지뿐이었다.

## 1. 매니페스트와 아이콘

Next.js App Router 는 `app/manifest.ts` 파일 하나로 매니페스트를 타입 세이프하게 서빙하고 `<head>` 연결까지 해준다.

```
// app/manifest.ts → /manifest.webmanifest 자동 서빙
export default function manifest(): MetadataRoute.Manifest {
  return { name: "LAYOUTNEMO — 캔버스 위 사고 공간", display: "standalone", ... }
}
```

아이콘은 기존 브랜드 SVG(`app/icon.svg`)에서 sharp 로 PNG 4종을 구웠다 — 192/512(일반), 512(maskable, 마스크가 모서리를 자르므로 full-bleed 배경 버전), 180(apple-touch-icon, iOS 는 PNG 만 받는다). sharp 는 next 의 의존성으로 이미 깔려 있어 추가 설치도 없었다.

## 2. 서비스워커 — 함정은 캐시가 아니라 "갱신"

서비스워커 라이브러리(next-pwa 등)를 쓸까 하다가 직접 썼다. 75줄이면 되는 일에 의존성과 추상화를 얹을 이유가 없었고, 무엇보다 **캐시 전략을 정확히 통제하고 싶었다**. 이 프로젝트의 진짜 리스크는 오프라인이 아니라 갱신이다 — 오늘만 배포가 7번인데, 캐시를 잘못 잡으면 사용자가 옛 버전에 갇힌다.

```
// 전략: HTML 은 network-first — 온라인이면 무조건 최신 배포
navigate  → fetch 시도 → 성공 시 캐시 갱신 / 실패(오프라인) 시 캐시 폴백
/_next/static, /icons → cache-first (해시 불변 — 바뀌면 URL 이 바뀐다)
/api, /auth, 크로스오리진(Supabase·Google) → 가로채지 않음
```

HTML 을 network-first 로 두면 "새 버전 알림 → 새로고침 유도" 같은 갱신 UX 를 만들 필요 자체가 없어진다. 온라인 사용자는 항상 최신이고, 캐시는 오프라인일 때만 나선다. 대신 재방문 속도 이득은 해시된 정적 자산의 cache-first 가 담당한다 — 역할 분담이 명확하다.

`/api` 를 가로채지 않는 건 협상 불가 조건이다. AI 응답이 캐시되면 어제의 정리하기 제안이 오늘 돌아오고, 동기화 요청이 캐시되면 데이터가 꼬인다.

## 3. iOS 의 몫

iOS 는 설치 배너가 없어서 사용자가 공유 버튼 → "홈 화면에 추가"를 직접 눌러야 한다. 첫 방문 환영 모달에 iOS Safari 사용자에게만 보이는 한 줄 안내를 넣었다. 감지가 살짝 재밌는데:

```
// iPadOS 는 UA 가 "Macintosh" 로 나온다 — 터치점 수로 구분
const isIOS = /iPad|iPhone|iPod/.test(ua) || (ua.includes("Macintosh") && navigator.maxTouchPoints > 1)
// 이미 설치돼 standalone 으로 실행 중이면 안내하지 않음
```

서비스워커는 프로덕션에서만 등록한다 — dev 에서는 HMR 과 캐시가 서로를 미치게 만든다.

## 4. 후속 — 기능이 있어도 아무도 모른다면

배포 직후 실기기에서 잘 되는 걸 확인하고 바로 나온 질문: **"일반 유저들한테는 이런 안내가 어떻게 나가?"** 답은 부끄럽게도 "거의 안 나간다"였다. Android 는 주소창 구석의 조용한 아이콘뿐이고, iOS 는 자동 안내가 아예 없으며, 우리가 넣은 환영 모달 안내는 첫 방문자만 본다.

그래서 상시 진입점을 만들었다 — About 다이얼로그에 "앱으로 설치" 섹션:

```
// Chrome/Edge: beforeinstallprompt 를 잡아뒀다가 버튼 클릭 시 우리가 띄운다 (원클릭 설치)
// iOS: 공유 → "홈 화면에 추가" 안내 문구
// 이미 설치했거나 standalone 실행 중이면 섹션 숨김
```

그리고 이 과정에서 구멍 하나 — About 을 여는 헤더의 ⓘ 버튼이 **데스크톱 전용으로 숨겨져 있었다**. 정작 설치 안내가 필요한 태블릿/휴대폰에서 진입점 자체가 안 보였던 것. 모든 기기에서 보이게 풀었다.

**회귀 하나도 이날 잡았다**: iOS 아이콘을 metadata `icons.apple` 로 명시하자 **파비콘이 사라졌다**. Next.js 는 `icons` 필드를 명시하면 `app/icon.svg` 자동 등록을 병합이 아니라 **대체**한다 — apple 만 적으면 rel="icon" 링크가 통째로 빠진다. icon 을 함께 명시해 복구(+PNG 폴백). 부분만 적어도 되는 것처럼 생긴 API 가 사실은 전체 교체인 경우, 문서보다 배포 후 탭 아이콘이 먼저 알려준다.

## 정리

- **"앱으로 만들기"는 하나의 결정이 아니라 사다리다.** PWA → Capacitor → 네이티브. 아래 칸의 작업물(매니페스트·아이콘·오프라인 전략)은 위 칸에서 전부 재사용된다.
- **배포가 잦은 앱의 서비스워커는 "오프라인"보다 "갱신"을 먼저 설계해야 한다.** HTML network-first 는 갱신 문제를 UX 로 풀지 않고 구조로 푼다.
- **API 는 캐시 대상이 아니라 캐시 금지 대상이다.** 가로채지 않는 게 가장 안전한 캐시 정책일 때가 있다.
- 75줄이면 되는 일에 라이브러리를 쓰지 않는 것도 기술 선택이다. 대신 그 75줄은 전부 이해하고 있어야 한다.

- **기능의 마지막 단계는 발견 가능성이다.** 설치 기능이 완벽해도 진입점이 데스크톱 전용이면 모바일에선 존재하지 않는 기능이다.

롤백 지점은 `release/pre-pwa`(본체)·`release/pre-pwa-install`(진입점). 홈 화면 설치·전체화면 실행은 실기기 확인 완료.
