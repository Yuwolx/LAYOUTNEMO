## 무슨 일이 있었나

로그인과 멀티 디바이스 동기화를 붙인 뒤, 한쪽 기기에서는 저장된 것처럼 보이는데 다른 기기에서는 반영되지 않는 문제가 나왔다. 더 나쁜 증상도 있었다. 캔버스에 있던 블럭들이 어느 순간 사라지고, 초기화해도 잠깐 보였다가 다시 없어지는 식이었다.

처음에는 로그인 마이그레이션이나 계정별 로컬 캐시가 꼬인 문제처럼 보였다. 실제로 그쪽도 위험한 지점이 있었다. 그래서 로컬 캐시가 어느 계정의 데이터인지 표시하도록 고쳤고, 다른 계정의 로컬 데이터를 새 계정에 병합하지 않도록 막았다.

하지만 그걸로 끝이 아니었다. 콘솔에는 이런 경고가 남아 있었다.

```text
[sync] 3개 캔버스에서 충돌 발생. 다른 기기의 최신 버전을 사용합니다.
```

충돌 자체는 의도한 동작이었다. 문제는 그 뒤에도 블럭이 사라진다는 점이었다.

---

## 원인: 저장 함수가 삭제까지 맡고 있었다

핵심은 `saveCanvas()`였다.

이 함수는 캔버스 하나의 현재 상태를 Supabase에 저장한다. canvas row를 upsert하고, zones와 blocks도 upsert한다. 여기까지는 자연스럽다.

문제는 그 다음이었다. 저장 함수가 "현재 캔버스 스냅샷에 없는 row는 삭제된 것"으로 보고 DB에서 지우고 있었다.

```typescript
// 개념적으로는 이런 구조였다.
await upsert(currentBlocks)
await deleteBlocksNotIn(currentBlockIds)
```

한 기기만 쓰면 대체로 문제가 없다. 현재 화면 상태가 곧 최신 상태이기 때문이다.

하지만 멀티 디바이스에서는 다르다.

예를 들어 A 기기에서 새 블럭을 만들고, B 기기가 조금 오래된 캔버스 상태를 들고 있다고 하자. B 기기가 자동 저장을 실행하면 B의 스냅샷에는 A에서 만든 새 블럭이 없다. 기존 로직은 이걸 "삭제된 블럭"으로 해석할 수 있었다.

즉, 오래된 저장이 최신 데이터를 지울 수 있는 구조였다.

[이전 로그인·DB 코드 리뷰 글]({{ site.baseurl }}/docs/devlog/2026-06-09-auth-db-code-review/)에서 이미 "전체 동기화 방식 자체에 경쟁 조건 여지가 있다"고 적어두었는데, 이번에는 그 위험이 실제 사용자 증상으로 드러난 셈이다.

---

## 수정: 저장과 삭제를 분리했다

이번에 고친 방향은 단순하다.

**일반 저장은 삭제하지 않는다.**

`saveCanvas()`에서 blocks pruning을 제거했다. 이제 자동 저장은 현재 블럭들을 upsert할 뿐, 스냅샷에 없다는 이유로 기존 block row를 지우지 않는다.

대신 사용자가 명시적으로 삭제한 경우만 별도 삭제 API를 탄다.

```typescript
export async function deleteBlocks(supabase, blockIds) {
  if (blockIds.length === 0) return
  await supabase.from("blocks").delete().in("id", blockIds)
}
```

갈무리함에서 블럭 하나를 지우거나, 갈무리함을 한 번에 비우는 경우는 명시적 삭제다. 이때만 `deleteBlocks()`를 호출한다.

이 차이가 중요하다.

- 자동 저장: 지금 알고 있는 상태를 서버에 반영한다.
- 명시적 삭제: 사용자가 삭제하겠다고 한 대상만 서버에서 지운다.

저장 함수가 삭제까지 겸하던 구조를 끊으니, 오래된 탭이나 다른 기기의 자동 저장이 최신 블럭을 지우는 경로가 사라졌다.

---

## 같이 고친 것: 실패를 숨기지 않기

이번 문제에서 사용자 경험을 더 헷갈리게 만든 건 "저장됨" 표시였다.

로컬 저장은 성공하고 있었기 때문에 화면에는 저장된 것처럼 보였다. 하지만 클라우드 저장이 실패하면 다른 기기에는 반영되지 않는다. 이 상태를 콘솔에만 찍으면 사용자는 알 방법이 없다.

그래서 로그인 직후 로드 실패뿐 아니라 자동 저장 실패도 토스트로 보이게 했다.

```typescript
toast.error("클라우드 저장에 실패했어요. 이 기기에는 저장되지만 다른 기기에는 아직 반영되지 않았어요.")
```

완전한 해결은 재시도 큐와 충돌 복구 UI까지 가야 한다. 그래도 최소한 "성공한 줄 알았는데 아니었다"는 상태는 줄였다.

---

## 같이 고친 것: 남아 있는 자동 저장 타이머

자동 저장은 2초 debounce로 동작한다. 상태가 바뀌면 바로 서버에 쓰지 않고, 잠깐 기다렸다가 한 번에 저장한다.

이 방식 자체는 괜찮다. 문제는 로그인/로그아웃, 동기화 준비 상태 전환 중에 이전 타이머가 남아 있을 수 있다는 점이었다.

그래서 effect 시작과 cleanup에서 pending timer를 확실히 정리했다. 이제 동기화 준비가 안 된 세션이나 이전 로그인 상태의 저장 요청이 늦게 실행될 가능성을 줄였다.

## 아직 남은 것

이번 수정으로 블럭이 사라지던 직접 경로는 막았다. 하지만 동기화 구조가 완전히 끝난 건 아니다.

### zones도 같은 냄새가 남아 있다

`blocks` 쪽 pruning은 제거했지만, `zones` 쪽에는 아직 "현재 스냅샷에 없는 결 삭제" 로직이 남아 있다. 결 삭제 기능과 직접 연결되어 있어서 바로 제거하면 사용자가 결을 삭제해도 서버에 남을 수 있다.

다음 정리는 zones도 blocks처럼 명시적 삭제 API로 분리하는 것이다.

### 삭제 tombstone은 아직 없다

캔버스 삭제는 여전히 row를 실제로 지운다. 그래서 오프라인 기기가 오래된 로컬 캔버스를 들고 있다가 나중에 재로그인하면, 삭제된 캔버스를 "새로 추가할 로컬 데이터"로 해석할 여지가 있다.

정석은 삭제 기록, 즉 tombstone을 남기는 것이다. 지금 규모에서는 바로 넣지 않았지만, 멀티 디바이스를 진지하게 가져가려면 결국 필요한 구조다.

### 재시도 큐도 없다

클라우드 저장 실패를 사용자에게 알리기는 하지만, 실패한 저장을 큐에 넣고 네트워크가 돌아왔을 때 자동 재시도하는 구조는 아직 없다.

지금은 "조용히 실패하지 않기"까지다.

---

## 정리

이번 수정의 핵심은 기능 추가가 아니라 책임 분리였다.

이전 구조에서는 `saveCanvas()`가 저장과 삭제를 동시에 맡았다. 단일 기기에서는 편한 구조지만, 멀티 디바이스에서는 오래된 스냅샷이 최신 데이터를 지울 수 있다.

그래서 일반 저장은 upsert만 하게 바꾸고, 실제 삭제는 사용자의 명시적 삭제 액션에서만 일어나게 했다. 동시에 클라우드 저장 실패를 토스트로 드러내고, 로그인 전환 중 남을 수 있는 자동 저장 타이머도 정리했다.

이번에 배운 것:

- "현재 상태 전체 저장"은 구현이 쉽지만 멀티 디바이스에서는 삭제 semantics가 위험하다.
- 삭제는 저장의 부작용이 아니라 별도 이벤트로 다뤄야 한다.
- 로컬 저장 성공과 클라우드 저장 성공은 사용자에게 다르게 보여야 한다.
- 운영 중인 동기화 버그는 로컬 테스트보다 실제 배포 환경에서 더 빨리 드러난다.

다음 우선순위는 zones 삭제 분리, 캔버스 삭제 tombstone, 저장 재시도 큐다. 동기화는 한 번에 완성되는 기능이 아니라, 실패 케이스를 발견할 때마다 데이터 유실 경로를 하나씩 줄여가는 쪽에 가깝다.
