오늘 작업은 아주 작은 불편에서 시작했다.

> "새 블럭을 만들었는데 내가 보고 있는 곳이 아니라 엉뚱한 데 생긴다."

캔버스형 도구에서는 이게 꽤 치명적이다. 사용자는 이미 눈으로 작업 공간을 잡고 있는데, 시스템이 새 블럭을 다른 좌표에 만들면 생각의 흐름이 끊긴다. 그래서 이번 사이클의 기준은 단순했다.

**새 블럭은 사용자가 지금 보고 있는 화면 안에서 생겨야 한다.**

---

## 1. 기존 문제 — 스마트 배치가 너무 자기 생각을 했다

기존 `findSmartPosition()` 은 같은 결(Facet)의 마지막 블럭을 찾아 그 오른쪽이나 아래에 새 블럭을 붙였다.

아이디어 자체는 좋았다. 같은 맥락끼리 모아주는 느낌이 있으니까.

문제는 두 가지였다.

1. **가이드 블럭을 충돌 계산에서 제외했다.**
2. **현재 viewport를 몰랐다.**

첫 번째 때문에 새 블럭이 기본 사용 설명서 블럭 위에 겹쳐질 수 있었다. 가이드 블럭은 삭제 가능한 안내물이긴 하지만, 화면 위에 실제로 존재하는 블럭이다. 배치 엔진이 "사용자에게 보이는 물체"를 무시하면 안 된다.

두 번째는 더 컸다. 사용자가 캔버스를 팬해서 오른쪽 아래를 보고 있어도, 새 블럭 위치 추천은 전체 world 좌표만 기준으로 움직였다. 그러면 사용자가 보고 있지 않은 곳에 블럭이 생길 수 있었다.

---

## 2. viewport를 부모 상태로 올리기

Canvas 내부에는 이미 `pan` 이 있었다. 하지만 새 블럭 생성 다이얼로그는 Canvas 밖에 있고, `findSmartPosition()` 도 다이얼로그 안에 있었다. 그래서 다이얼로그는 현재 화면이 world 좌표로 어디인지 알 수 없었다.

해결은 작게 했다.

- `CanvasViewport` 타입 추가
- Canvas가 `pan` 과 DOM rect를 기준으로 현재 보이는 world 좌표를 계산
- 부모 `page.tsx` 가 그 값을 들고 있다가 `CreateBlockDialog` 로 전달

```ts
export interface CanvasViewport {
  x: number
  y: number
  width: number
  height: number
}
```

이렇게 넘긴 뒤, 새 블럭 후보는 `visibleCanvasBounds` 안에서만 고른다.

---

## 3. 기본 블럭도 충돌 대상으로

기존 코드는 활성 블럭을 이렇게 걸렀다.

```ts
const activeBlocks = existingBlocks.filter(
  (b) => !b.isDeleted && !b.isCompleted && !b.isGuide
)
```

이번에는 `isGuide` 를 제외하지 않는다.

```ts
const layoutBlocks = existingBlocks.filter(
  (b) => !b.isDeleted && !b.isCompleted
)
```

가이드 블럭도 화면 위 물체다. 새 블럭 배치가 피해야 한다.

---

## 4. "직접 옮기기" 시작점도 현재 화면 안으로

이전에는 수동 배치 시작점이 거의 임의 좌표였다.

```ts
{ x: 300 + Math.random() * 400, y: 200 + Math.random() * 300 }
```

이제는 수동 배치도 현재 viewport 안에서 시작한다. 사용자가 직접 옮기겠다고 해도, 출발점이 화면 밖이면 이미 불친절하다.

자동 생성, 추천 위치, 직접 옮기기 시작 위치가 모두 같은 원칙을 공유하게 됐다.

---

## 5. 갈무리 보기 버튼 제거

헤더에 있던 "갈무리 보기" 토글도 제거했다.

갈무리 UX는 이미 우하단 독과 모달로 방향이 바뀌었다. 그러면 헤더 토글은 역할이 애매하다. "캔버스에 갈무리 블럭을 다시 보이게 하는 버튼"처럼 읽히지만, 현재 제품 철학은 갈무리된 블럭을 캔버스 밖 별도 공간에 둔다.

그래서 버튼을 지웠다.

남긴 것은 하나다.

- 우하단 갈무리 독
- 독 클릭 시 갈무리함 모달
- 갈무리함에서 다시 꺼내기

---

## 6. 기본 배율 — Cmd-minus 한 번의 느낌

사용자가 매번 브라우저에서 `Cmd -` 를 한 번 눌러 쓰고 있었다.

이건 꽤 좋은 신호다. "UI가 싫다"보다 더 구체적이다. 사용자가 이미 자기 손으로 적정 밀도를 찾은 상태였으니까.

그래서 캔버스 기본 배율을 `0.9` 로 잡았다.

```ts
const DEFAULT_CANVAS_SCALE = 0.9
```

단순히 CSS `scale(0.9)` 만 넣으면 끝이 아니다. 좌표계가 같이 움직여야 한다.

- 블럭 드래그 좌표
- 갈무리 독 drop hit-test
- 현재 viewport 계산
- 새 블럭 위치 추천
- 배경 도트 간격

이 전부를 `DEFAULT_CANVAS_SCALE` 기준으로 보정했다.

---

## 7. 블럭 상세와 결 강조

블럭을 클릭했을 때 나오는 상세 다이얼로그도 키웠다.

작은 카드 위에서는 요약만 보는 게 맞지만, 클릭해서 들어간 순간에는 "읽고 편집하는 화면"이 되어야 한다. 그래서 상세 다이얼로그 폭과 textarea 높이를 늘렸다.

결을 눌렀을 때 해당 결 블럭이 더 크게 강조되는 것도 유지했다. 다만 오늘 중간에 "전체 기본 배율"과 "결 선택 확대"를 헷갈려 한 번 잘못 만졌다. 결 선택 확대는 원래 의도대로 별도 개념이고, 기본 배율은 캔버스 전체 밀도 문제다.

---

## 8. 시급도 재정의 — 미정 / 여유 / 진행 / 시급

마지막으로 시급도 네 단계를 다시 잡았다.

기존의 "생각 중", "머물러 있음"은 의미가 조금 흐렸다. 특히 "머물러 있음"은 사용자가 직접 고르기엔 상태가 애매했다. 그래서 이번에는 실제 선택 순간에 더 자연스럽게 읽히는 네 단어로 정리했다.

| 단계 | 라벨 | 의미 | 색상 |
|------|------|------|------|
| 1 | **미정** | 일단 적어뒀지만 할지 말지 아직 모르는 일 | 🔵 파랑 |
| 2 | **여유** | 할 일은 맞지만 급하지 않은 일 | ⚪ 회색 |
| 3 | **진행** | 꾸준히 진행하거나 계속 관리 중인 일 | 🟡 노랑 |
| 4 | **시급** | 바로 처리해야 하는 일 | 🟠 주황 |

내부 저장 키는 기존 데이터 호환을 위해 그대로 둔다.

- `thinking` → 미정
- `stable` → 여유
- `lingering` → 진행
- `urgent` → 시급

라벨만 바꾼 건 아니다. 생성 다이얼로그, 상세 다이얼로그, 카드 fallback, 기본 가이드 문구, AI 프롬프트, 로컬 fallback 키워드까지 같은 기준으로 맞췄다. 새 블럭의 기본값도 "여유"가 아니라 "미정"으로 바꿨다. 처음 적는 생각은 대개 확정된 일이 아니라 "일단 적어둔 것"에 더 가깝기 때문이다.

---

## 오늘 기준 상태

- `develop` 에서 작업 중
- 빌드 통과
- 로컬 서버에서 검증 중
- 시급도 4단계는 `미정 / 여유 / 진행 / 시급` 기준으로 재정의
- 아직 `master` 머지 전

이번 작업의 핵심은 "똑똑한 배치"가 아니라 **사용자가 지금 보고 있는 공간을 존중하는 배치**다. 캔버스 도구는 좌표를 다루는 도구이기 전에 시선을 다루는 도구다.
