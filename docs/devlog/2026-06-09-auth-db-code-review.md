## 왜 지금 점검하나

소셜 로그인, 멀티 디바이스 동기화, 관리자 대시보드까지 — 기능은 다 붙었다. 배포 후 첫날 터진 버그들도 [전부 잡았다]({{ site.baseurl }}/docs/devlog/2026-06-09-v2-first-patch/).

기능이 "동작한다"와 "잘 짜였다"는 다른 질문이다. 더 쌓기 전에 인증/DB 레이어를 통째로 다시 읽었다. 결과를 가감 없이 적는다. 다만 운영 중인 서비스라 구체적인 공격 경로로 이어질 수 있는 디테일은 여기서 빼고, "이런 종류의 한계가 있다 / 우선순위는 이렇게 잡았다" 수준으로 정리한다.

---

## 잘 짜인 부분

### RLS가 마지막 방어선

모든 테이블에 Row Level Security가 걸려있다. 앱 코드에서 필터를 빼먹는 버그를 내더라도, DB가 본인 데이터 밖으로 못 나가게 막는다. 코드 레이어와 DB 레이어, 두 겹으로 방어선을 친다는 게 핵심이다.

### 권한 상승 키는 정말로 한 곳에만 있다

RLS를 우회하는 service role key가 코드베이스 어디에 새고 있는지 전체를 그렙으로 훑었다. 결과는 서버 전용 라우트 단 한 곳. 클라이언트 코드, 다른 API 라우트, 어디에도 노출되어 있지 않았다. "서버 전용 키는 절대 클라이언트에 노출하지 않는다"는 원칙이 실제로 지켜지고 있는지 검증한 셈이다.

### 관리자 권한 체크를 별도 함수로 분리

관리자가 전체 유저 데이터를 읽어야 하는데, RLS 정책 안에서 권한 테이블을 직접 참조하면 재귀 평가 문제가 생긴다. `security definer` 함수로 한 단계 분리해서 이 문제를 피했다.

### Supabase 없으면 조용히 꺼진다

환경변수가 비어있으면 인증 컨텍스트 전체가 로그인 버튼도 안 보여주고 로컬 모드로만 동작한다. 개발 환경에서 키를 안 넣어도 앱이 안 죽는다. 외부 의존성이 없을 때 우아하게 degrade하는 설계.

## 발견한 문제

### 1. 동기화 실패가 조용히 영구화된다 (가장 심각)

로그인 직후 서버에서 캔버스를 불러오는 코드가 `try/catch`로 감싸져 있는데, 실패 시 처리가 이랬다.

```typescript
} catch (err) {
  console.error("Supabase load error:", err)
  // 실패해도 로컬 데이터로 계속 동작
}
```

문제는 이 catch에 걸리면 "이번 세션은 서버와 동기화 준비가 안 됐다"는 내부 플래그가 계속 꺼진 상태로 남는다는 것. 이 플래그가 꺼져 있으면 이후의 모든 저장 동작(즉시 저장, 2초 후 자동 저장 둘 다)이 조용히 아무것도 안 한다.

그런데 화면에 뜨는 "저장됨" 표시는 로컬 저장 기준이라 계속 정상적으로 갱신된다. 사용자 입장에서는 평소처럼 보이는데, 실제로는 그 세션 내내 클라우드에 단 한 번도 안 쓰여지고 있는 상태다. 네트워크가 잠깐 끊기거나 서버가 일시적으로 느렸던 것뿐인데, 새로고침 전까지 복구가 안 된다.

다른 기기에서 로그인했을 때 방금 한 작업이 안 보이는 사고로 이어질 수 있는 종류라 가장 먼저 고쳤다. 토스트로 사용자에게 알리도록 추가했다 — 근본적으로는 재시도 로직이 필요하지만, 일단 "조용히 실패하지 않기"부터.

```typescript
toast.error("클라우드 동기화에 실패했어요. 이 기기에는 저장되지만 다른 기기에는 반영되지 않아요.")
```

### 2. 마이그레이션 순서 버그 (이 리뷰 중에 직접 만든 것)

며칠 전 관리자 대시보드에 유저 이메일이 안 뜨는 문제를 고쳤다. 그때 신규 가입 트리거에 email 컬럼 삽입 로직을 추가했는데, **잘못된 마이그레이션 파일**에 적용했다. 그 컬럼은 사실 더 나중 마이그레이션에서야 테이블에 추가되는데, 먼저 실행되는 파일의 트리거가 그 컬럼을 참조하고 있었던 것.

실제 운영 환경에서는 마이그레이션 파일들이 항상 순서대로 한 번에 실행되니 문제가 드러나지 않았다. 하지만 마이그레이션 파일은 "그 시점의 스키마에 맞는 코드"여야 한다는 원칙을 깬 거다. 이번 리뷰 중에 발견해서, 컬럼이 아직 없는 시점에 맞게 되돌렸다.

가장 빠르게 잡은 버그가, 가장 최근에 내가 만든 버그였다.

### 3. 동기화에 "삭제됐다"는 기록이 없다

충돌 해결 전략은 "로그아웃 시점 이후 양쪽 다 바뀌었으면 서버 우선"이다. 단순하고 대부분 잘 맞는다.

문제는 **삭제**다. 한 기기에서 캔버스를 삭제하고, 다른 기기가 오프라인 상태로 그 캔버스를 들고 있다가 나중에 로그인하면, 병합 로직이 이걸 "서버엔 없지만 로컬에는 있는 항목"으로 보고 새로 만든 것으로 해석할 수 있다. 그러면 삭제가 무효화되고 캔버스가 부활한다.

제대로 고치려면 "삭제됐었다"는 사실 자체를 기록하는 tombstone(삭제 마커)이 필요하다. 지금은 row를 진짜로 지우기 때문에 그 흔적이 안 남는다. 멀티 디바이스를 켜놓고 오프라인 작업을 자주 하는 사용자가 아니면 마주치기 어려운 케이스라 당장 고치진 않았다. 알고 있는 빚으로 남긴다.

### 4. "전체 동기화" 방식 자체에 경쟁 조건 여지가 있다

캔버스를 저장할 때 zones/blocks를 통째로 올리고, 현재 목록에 없는 row를 지우는 방식을 쓴다. 두 개의 저장이 거의 동시에 일어나면(예: 두 탭, 또는 빠르게 연속된 액션), 한쪽이 막 추가한 row를 다른 쪽의 "목록에 없으면 지운다" 로직이 지워버릴 수 있다. [이전 글에서 정리한 이중 저장 버그]({{ site.baseurl }}/docs/devlog/2026-06-09-v2-first-patch/)를 고치면서 빈도는 크게 줄었지만, 구조적으로는 남아있는 위험이다.

근본적인 해결은 "현재 상태 전체를 매번 동기화"가 아니라 "무엇이 추가/삭제됐는지"를 따로 추적하는 것이다. 지금 규모에서는 과한 작업이라 보류.

### 5. 값을 쿼리 필터에 직접 끼워 넣는 곳이 있다

일부 쿼리에서 ID 목록을 문자열로 합쳐 필터 조건에 직접 넣는 패턴을 쓰고 있다. 지금은 안전하다 — 모든 ID가 서버가 발급한 UUID이고 사용자 입력이 끼어들 자리가 없다. 하지만 "값을 쿼리 문자열에 직접 꽂아 넣는" 습관 자체는, 나중에 누군가(혹은 AI가) 이 패턴을 사용자 입력이 들어가는 곳에 그대로 복붙하면 인젝션 통로가 될 수 있는 종류다. 지금 고칠 시급함은 없지만, 다른 곳에 복붙되지 않도록 표시해뒀다.

### 6. 관리자 인증이 더 견고해질 수 있는 여지가 있다

지금 관리자 로그인은 별도 세션 토큰을 발급하지 않고, 환경변수 값 자체를 쿠키 검증에 쓰는 방식이다. httpOnly + secure + sameSite 같은 기본 방어는 되어 있지만, 토큰을 별도로 발급하는 구조였다면 유출 시 비밀번호를 바꾸지 않고 토큰만 무효화할 수 있다. 혼자 운영하는 관리자 페이지 규모에서는 당장 큰 위험은 아니지만, 다음 정리 대상으로 기록.

## 정리

이번 점검에서 나온 것: 데이터 유실로 이어질 수 있는 진짜 버그 2개(동기화 무한 침묵, 마이그레이션 순서 — 둘 다 바로 고침), 구조적 한계 2개(삭제 동기화, 동시 쓰기), 패턴 문제 1개, 보안 강화 여지 1개.

가장 심각했던 건 "동기화가 실패해도 사용자는 알 방법이 없다"는 1번이었다. RLS나 권한 설계처럼 눈에 보이는 보안 문제보다, 조용히 실패하는 에러 처리가 실제로는 더 위험하다는 걸 다시 확인했다.

남은 구조적 한계(삭제 동기화, 동시 쓰기)는 "지금 규모에서는 안 터지는 버그"와 "절대 안 터지는 버그"가 다르다는 전제로 남겨뒀다. 사용자가 늘고 멀티 디바이스 사용이 늘면 먼저 드러날 가능성이 높은 곳이라 적어둔다.

다음 정리 타이밍 우선순위: 삭제 동기화 구조 개선 → 관리자 인증 토큰화 → AI rate limit. 셋 다 정책 결정이 코드보다 먼저 필요한 일들이다.
