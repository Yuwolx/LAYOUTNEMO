## 무슨 일이 있었나

이번 작업은 새 기능을 크게 붙이는 쪽이 아니었다. 코드나 스키마에 **이미 존재하는데 실제로는 연결되지 않아** 동작하지 않던 것들을 하나씩 이어 붙이는 쪽이었다.

세 가지가 그랬다.

- AI 사용량 한도: 제한하려고 만들어 둔 DB 컬럼이 있는데, 아무도 읽거나 늘리지 않았다.
- 관리자 대시보드의 AI 사용량 집계: 이벤트를 기록하는 코드가 있는데, 실제로는 요청이 나가지 않았다.
- 온보딩: 전체 사용 설명서가 이미 캔버스에 있는데, 처음 온 사람이 그걸 발견할 길이 없었다.

## AI 한도: 컬럼만 있고 코드가 없었다

`user_profiles`에는 처음부터 `ai_create_used`, `ai_create_reset_at` 같은 컬럼이 있었다. 무료 플랜의 월 사용량을 제한하려고 만들어 둔 것이다.

그런데 AI 블럭 생성 라우트를 뜯어보니, 이 컬럼을 **읽지도 늘리지도 않고** 있었다. 즉 로그인만 하면 AI 생성은 사실상 무제한이었다. OpenAI 키는 내 것이니, 이건 그대로 두면 비용이 새는 구멍이다.

제한 자체보다 신경 쓴 건 **정확성**이었다. "사용량을 읽어서 → 한도랑 비교하고 → 1 늘린다"를 애플리케이션 코드에서 하면, 동시에 두 요청이 들어올 때 한도를 넘길 수 있다. 그래서 이 셋을 **DB 함수 한 번의 원자적 UPDATE**로 묶었다.

```sql
update user_profiles
  set ai_create_used = ai_create_used + 1
  where id = auth.uid()
    and (plan = 'pro' or ai_create_used < p_limit)
  returning ...;
-- 0행 갱신 = 한도 초과
```

`where` 조건 안에 한도 검사를 넣었기 때문에, 동시 요청이 들어와도 각 UPDATE가 최신 값을 다시 확인한다. 경계에서 한도를 넘길 수 없다.

나머지는 이 함수에 같이 얹었다.

- **월 리셋**: 리셋 시각이 지났으면 접근 시점에 카운터를 0으로 되돌린다. 크론이 필요 없다.
- **환불**: OpenAI 호출이 끝내 실패하면 예약했던 1을 돌려준다. 실패한 호출이 사용량을 깎지 않도록.
- **fail-open**: 쿼터 함수 자체가 아직 배포 안 됐거나 에러가 나면, 사용자를 막기보다 통과시키고 로그만 남긴다. 한도 시스템 때문에 AI 전체가 죽는 게 더 나쁘니까.

지금 무료 플랜 기준은 생성 300회, 정리하기 10회. `pro`는 무제한으로 분기해 뒀다.

## 사용량 집계: 부르긴 하는데 요청이 안 나갔다

관리자 대시보드에 AI 사용량이 계속 0으로 찍혔다. 처음엔 집계 쿼리를 의심했는데, 쿼리는 멀쩡했다.

문제는 **이벤트를 기록하는 쪽**이었다. AI 라우트는 이렇게 이벤트를 남기고 있었다.

```typescript
supabase.from("events").insert({ user_id, name: "ai_create_used", payload: {} })
```

언뜻 정상처럼 보인다. 하지만 supabase-js의 쿼리 빌더는 **`await` 하거나 `.then()`을 붙일 때 비로소 실제 요청을 보낸다.** 위 코드는 둘 다 없다. 그래서 이 insert는 **요청 자체가 나가지 않았다.** 이벤트가 유실된 게 아니라, 애초에 만들어지지 않았다.

대비되는 건 세션/블럭 이벤트를 남기는 `captureEvent` 헬퍼였다. 이쪽은 `.then()`이 붙어 있었다.

```typescript
supabase.from("events").insert({ ... }).then(({ error }) => { ... })
```

그래서 세션이나 블럭 생성 집계는 정상이었고, **AI만** 0이었다. 증상이 딱 그 모양이었던 이유다.

수정은 단순하다. 두 AI 라우트의 insert를 `await` 하고, 그 실패가 이미 성공한 AI 응답에 영향을 주지 않도록 자체 `try/catch`로 감쌌다.

```typescript
try {
  await supabase.from("events").insert({ user_id, name: "ai_create_used", payload: {} })
} catch (e) {
  console.error("event insert failed:", e)
}
```

`await`를 붙이는 건 서버리스에서 응답 반환 뒤 프로미스가 잘리는 것도 같이 막아 준다. 이제 배포 후부터 대시보드에 생성/정리하기 횟수가 잡힌다.

## 첫 인사: 콘텐츠는 있었고, 발견성이 없었다

온보딩을 붙이려고 보니, 사실 설명 콘텐츠는 이미 다 있었다. 첫 캔버스에는 12단계짜리 "사용 설명서" 가이드 블럭이 한/영으로 시드되어 있었다.

문제는 처음 온 사람이 그걸 **클릭해야 한다는 걸 모른다는 것**이었다. 예시 블럭들 사이에 섞여 있으니 그냥 지나치기 쉬웠다.

그래서 새 튜토리얼 시스템을 만드는 대신, **이미 있는 가이드로 유도하는 첫 방문 환영 모달**을 붙였다. 핵심 개념 네 가지(블럭 · 결 · 연결 · 시급도)를 간단히 소개하고, "가이드 보기"를 누르면 같은 모달 안에서 그 12단계 매뉴얼을 그대로 펼친다. 시급도는 실제 블럭과 같은 색·글로우로 보여 줘서, 모달과 캔버스가 같은 언어를 쓰게 했다.

한 번 닫으면 다시 뜨지 않고, `?welcome`을 붙이면 언제든 다시 열 수 있다.

## 곁다리로 같이 손본 것

QA로 흐름을 훑다가 나온 것들도 같이 정리했다.

- **프로필 방어**: 로그인 시 `user_profiles` 행이 없으면 이후 캔버스/블럭 저장이 RLS에 조용히 막힌다. 트리거가 만들어 주긴 하지만, 혹시 실패했거나 구 계정이라 행이 없을 때를 대비해 로그인 시 "본인 행만 있으면 만든다(ON CONFLICT DO NOTHING)"를 한 번 태웠다.
- **관리자 로그인 rate limit**: IP당 15분 8회로 막았다. 서버리스라 인스턴스별 상태지만, 자동화 공격 속도는 의미 있게 늦춘다.
- **AI 입력 안내**: AI 생성 입력창에 "한 줄만 적어도 제목·요약·결·상태·기한·링크까지 정리해 준다"는 문구를 넣었다. 뭘 적어야 할지 모르는 첫 화면을 줄이려고.

## 정리

이번 작업을 관통하는 건 "없어서 못 한 것"이 아니라 "있는데 안 이어져 있던 것"이었다.

한도 컬럼은 스키마에 있었지만 코드가 읽지 않았고, 이벤트 기록은 호출됐지만 요청이 나가지 않았고, 사용 설명서는 캔버스에 있었지만 아무도 클릭하지 않았다. 셋 다 "존재"와 "동작" 사이가 비어 있었다.

이번에 배운 것:

- 스키마에 컬럼만 있고 쓰는 코드가 없으면, 그 기능은 없는 것이다.
- `await` 없는 supabase 쿼리는 유실되는 게 아니라 **실행 자체가 안 된다.** 이벤트·로그처럼 "안 나가도 티가 안 나는" 곳일수록 위험하다.
- 한도·차감 같은 건 애플리케이션이 아니라 DB의 원자적 연산으로 밀어 넣어야 경쟁 조건이 안 생긴다.
- 온보딩의 병목은 콘텐츠 부족이 아니라 발견성인 경우가 많다. 이미 있는 걸 잇는 게 새로 만드는 것보다 낫다.

다음은 정리하기 삭제 블럭 보존, 결 삭제 UX, Next 보안 패치 검토 쪽이다. 큰 기능을 얹기 전에, 이미 있는데 안 이어진 선부터 잇는 편이 대체로 남는 장사였다.
