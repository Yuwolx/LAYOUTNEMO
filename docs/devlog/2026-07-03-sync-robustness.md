## 무슨 일이 있었나

로드맵의 "동기화 견고성" 덩어리에 착수했다. 세 항목 — 캔버스 삭제 tombstone, 서버시간 충돌 판정, 저장 재시도 — 중 앞뒤 두 개를 이번에 처리했다.

## 1. 캔버스 부활 시나리오

블럭 유실은 [6월 29일에](2026-06-29-sync-pruning-fix.md) soft delete 로 막았다. 그런데 **캔버스 삭제는 여전히 hard delete** 였다:

```
기기 A: 캔버스 X 삭제 → DB 행 자체가 사라짐
기기 B: X 를 로컬에 쥔 채 autosave → saveCanvas 가 X 를 통째로 upsert
      → 행이 없으니 insert → 캔버스 부활 (블럭까지 전부)
```

지운 게 돌아오는 건 유실보다 소름 돋는 경험이다. 해결은 블럭과 같은 원리 — 행을 지우지 않고 **tombstone(삭제 마커)** 을 남긴다. 이 프로젝트 관례대로 컬럼 추가 없이 `canvases.metadata`(jsonb) 에 마킹했다:

```
// 삭제 = update metadata { deleted: true, deleted_at }
// 부활 불가 이유: saveCanvas 의 upsert 는 metadata 컬럼을 아예 안 쓴다
//   → 오래된 기기가 name/position 을 덮어써도 deleted 마커는 그대로 산다
// loadUserCanvases 가 tombstone 을 걸러서 어디에도 노출 안 됨
```

핵심은 **tombstone 이 저장 경로와 다른 컬럼에 산다**는 것. 같은 컬럼이었으면 오래된 기기의 upsert 가 마커까지 덮었을 것이다. "초기화"도 같은 이유로 hard delete 에서 tombstone 으로 바꿨다.

## 2. 한 번 실패하면 끝이던 저장

클라우드 autosave 는 실패하면 토스트 한 번 띄우고 끝이었다. 다음 재시도는 **사용자가 뭔가를 또 바꿔야만** 일어난다. 지하철에서 블럭 정리하고 폰을 주머니에 넣으면, 그 변경은 다른 기기에 영영 안 갈 수 있었다.

```
// 해결: 실패 → dirty 플래그 + 10초 뒤 재시도 (최신 상태 기준)
//       + 네트워크 복귀(online 이벤트) 시 즉시 재저장
//       + 실패 후 성공하면 "저장 재개" 토스트로 안심시키기
```

디테일 하나: 재시도는 실패한 시점의 스냅샷이 아니라 **재시도 시점의 최신 canvases** 를 저장한다(ref 미러). 실패한 옛 상태를 다시 밀면 그 사이의 변경을 되감아버린다.

## 3. 서버시간 충돌 판정은 안 했다

세 번째 항목은 의도적으로 미뤘다. 지금 updated_at 은 클라이언트 시계로 쓰는데, 이걸 서버 시간으로 바꾸려면 DB 트리거(마이그레이션)가 필요하고, 시계가 다른 기기 두 대로 라이브 검증을 해야 한다. 로컬에서 DB 동작을 검증할 수 없는 이 프로젝트 constraint 상, **"빌드는 통과하는데 실데이터에서 어떻게 도는지 모르는" 채로 배포하게 되는 종류의 변경**이다. 클라우드 우선 병합 구조에서 클라이언트 시계는 백업 알림 판단에만 쓰여 당장의 유실 위험도 아니고 — 동시 편집을 본격 지원하는 사이클에서 트리거 + 실기기 2대 검증으로 함께 간다.

## 정리

- **soft delete 를 한 엔티티에만 적용했다면, 같은 부활 통로가 다른 엔티티에 그대로 열려 있는지 봐야 한다.** 블럭은 막았는데 캔버스는 8개월간 열려 있었다.
- **tombstone 은 일반 저장 경로가 건드리지 않는 곳에 둬야 산다.** metadata 컬럼을 saveCanvas 가 안 쓴다는 사실이 이 설계의 전부다.
- **재시도는 실패한 스냅샷이 아니라 현재 상태로.** 옛 상태 재전송은 재시도가 아니라 롤백이다.
- 검증할 수 없는 변경을 검증할 수 있는 변경과 한 배에 태우지 않는다 — 서버시간 판정은 다음 배로.

롤백 지점은 `release/pre-sync-robustness`. 실기기 2대로 "A 에서 캔버스 삭제 → B 새로고침 후에도 안 돌아오는지" 확인이 남아 있다.
