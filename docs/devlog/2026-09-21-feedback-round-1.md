## 들어온 피드백

앱을 설치해 며칠 써본 지인이 보낸 목록을 요약하면 이렇다.

1. 창을 줄이면 헤더가 잘린다. 폰 같은 세로 화면엔 안 맞는 서비스 아닌가.
2. 시급도를 글로우로 보여주는 건 좋은데 라이트에선 안 보이고 다크에선 눈이 아프다. 블럭 색이나 라벨은 어떤가. 호버하면 신호등 점 3개가 떠서 바로 바꾸게 하면 어떤가.
3. 사용설명서·단축키 블럭이 평생 캔버스에 있어야 하나. 헤더에 ? 아이콘으로 빼자.
4. 스페이스+드래그 팬은 두 손이 필요하다. 휠클릭 드래그도 되게 해달라.
5. 이름은 영어(LAYOUTNEMO)인데 용어는 한글(결, 갈무리). 보관함·카테고리가 더 직관적이지 않나.
6. 갈무리를 거쳐야만 지울 수 있어 번거롭다. 휴지통, 드래그 앤 드롭, 잠금, 호버 갈무리 아이콘.
7. 드래그로 여러 개 선택해 옮기게 해달라.
8. 결 강조보다 연결된 블럭 강조가 낫지 않나.

## 먼저 코드와 대조했다

판정 전에 각 항목을 코드에서 찾아봤다. 이게 중요했던 이유는 절반이 "없는 기능"이 아니라 "못 찾은 기능"이었기 때문이다.

- 7번 다중 선택: Ctrl+드래그 마퀴와 선택 모드, 그룹 드래그가 전부 있다.
- 6번의 드래그 앤 드롭 갈무리: 우하단 갈무리함에 드롭 판정이 이미 있다.
- 1번 헤더 잘림: 헤더는 이미 가로 스크롤이다. 다만 마우스로는 드래그 스크롤이 안 되고 Shift+휠로만 밀려서, PWA 창을 줄여 쓴 사람은 못 찾았다. 폰(터치)에선 잘 된다.
- 6번의 잠금(pin): 지금 pin 은 "대표로 고정"이라 이름만 같고 다른 기능이다.

없는 기능이라고 믿고 만들었으면 두 번 만들었을 것이다. 못 찾은 기능은 발견성 문제이고, 그건 3번의 ? 도움말이 같이 풀어준다.

## 판정

사용자(나)의 결정은 짧았다.

- **받음**: 휠클릭 팬, 가이드 블럭 지우기 + ? 로 다시 불러오기, 글로우 가시성 조정, Shift 드래그로 즉시 삭제.
- **거절**: 호버 신호등 점("점 추가하는거 싫다"), 블럭 색·라벨, 휴지통 독("귀찮다"), 연결 강조("결 강조로 간다"), 잠금(홀드), 네이밍 변경, 헤더 재작업.

거절의 공통점은 하나다. 블럭 위에 뭔가를 더 얹는 제안은 전부 거절됐다. 캔버스의 시각 언어를 "색=의미, 질감은 동일, 부가 UI 최소"로 지켜온 결정이 그대로 기준이 됐다. 피드백을 받는 기준이 있으면 판정이 빠르다.

## 구현 1 — 휠클릭 팬

캔버스 pointerdown 이 `button !== 0` 이면 통째로 무시하고 있었다. 우클릭이 포인터를 영구 점유하는 맥 버그를 막으려고 넣은 가드다. 가운데 버튼만 그 앞에서 잡아 스페이스 팬과 같은 경로로 태웠다.

```ts
// 문제: button !== 0 은 전부 return → 휠클릭이 아무것도 안 함
// 해결: 가운데 버튼(mouse)만 팬 경로로. 블럭 위에서 시작해도 팬.
if (e.button === 1 && e.pointerType === "mouse") {
  e.preventDefault() // 윈도우 크롬의 중클릭 자동 스크롤 차단
  panStartRef.current = { mouseX: e.clientX, mouseY: e.clientY, panX: pan.x, panY: pan.y }
  activePointerIdRef.current = e.pointerId
  setIsPanning(true)
  return
}
if (e.button !== 0) return
```

블럭 카드의 핸들러는 원래 button 이 0 이 아니면 아무것도 안 하고 버블시키므로, 블럭 위에서 휠을 눌러도 캔버스까지 올라와 팬이 된다. 우클릭 무시는 그대로다.

## 구현 2 — Shift + 갈무리함 드롭 = 즉시 삭제

"Shift 드래그하면 사라지기"라는 요청이 왔는데, Shift 드래그는 이미 토스(다른 블럭 위에 놓으면 연결만 만들고 제자리로 복귀)에 쓰고 있었다. 셋 중 하나를 골라야 했다.

1. Shift 누른 채 갈무리함에 드롭하면 갈무리 대신 삭제
2. Shift 누른 채 빈 곳에 놓아도 삭제
3. 토스를 없애고 Shift 드래그 전체를 삭제로

1번으로 갔다. 손 뗄 때 갈무리함 판정이 토스 판정보다 먼저 돌기 때문에 코드상 겹치지 않고, 목적지가 갈무리함이라 실수로 지울 여지가 가장 작다. 삭제는 soft-delete(`isDeleted` 마킹)라 히스토리 한 커밋이고 Cmd/Ctrl+Z 로 돌아온다. 토스트로 그 사실을 알린다.

```ts
// 문제: 갈무리함 드롭은 무조건 isCompleted=true
// 해결: Shift 면 삭제 콜백으로. 삭제 전 원위치로 되돌려(히스토리 없이) undo 시 제자리에 서게.
const deleteNow = e.shiftKey && onDeleteBlockRef.current !== undefined
// ...날아가는 애니메이션 뒤
if (deleteNow) {
  onUpdateBlockRef.current(id, { x: restoreX, y: restoreY }, true)
  onDeleteBlockRef.current?.(id)
} else {
  onUpdateBlockRef.current(id, { isCompleted: true, x: restoreX, y: restoreY })
}
```

## 구현 3 — 가이드 블럭 해방

사용설명서·단축키 블럭은 `isGuide` 가드로 갈무리·복사·그룹 드래그에서 전부 빠져 있었고, 새 캔버스마다 다시 생성됐다. 무료 플랜이 캔버스 1개인데 그 안에 지울 수 없는 블럭이 둘 있는 셈이다.

가드를 풀어 케밥(갈무리만)과 갈무리함 드롭을 허용하고, 헤더 인사이트 옆에 ? 버튼을 뒀다. 누르면 보이는 화면 한가운데에 두 블럭이 나란히 생긴다. 이미 살아 있으면 그대로 두고, 갈무리돼 있으면 꺼내서 그쪽으로 시선을 옮긴다. 새 캔버스 생성은 tombstone 가이드를 건너뛰고 갈무리 상태를 풀어서 복제한다.

## 구현 4 — 글로우만 조정

라이트 그림자가 파스텔 단색 한 겹(예: `rgba(147,197,253,0.65)`)이었다. 연한 파랑을 흰 바닥에 0.65 로 깔아봐야 거의 안 보인다. 다크에서 이미 쓰던 2겹 구조(가까운 진한 광 + 넓은 은은한 광)를 라이트에도 적용하되 색은 한 단계 진한 톤(blue-400, green-400, red-400 계열)으로 바꿨다. 다크는 알파를 30% 정도 내렸다. 점·라벨·테두리는 넣지 않았다. `urgency.ts` 단일 소스라 바꾼 파일은 하나다.

## 테스트: jsdom 에서 갈무리함 드롭을 재현하기

포인터 상태 머신은 7월부터 vitest(jsdom)로 선제 검증한다. 이번엔 가운데 버튼 팬, 팬 후 포인터 해제, 우클릭 무시, Shift 유무별 삭제/갈무리 분기, 가이드 블럭 드롭까지 여덟 개를 추가했다.

갈무리함 드롭 판정이 문제였다. 캔버스는 `[data-archive-dock]` 요소의 `getBoundingClientRect` 로 드롭 위치를 판정하는데 jsdom 은 전부 0 을 돌려준다. 그런데 블럭 좌표도 0 에서 시작하니, 독 요소만 DOM 에 넣어두면 어떤 드롭도 "독 위"로 판정된다. 판정 자체는 검증 못 하지만 그 뒤의 분기(Shift 면 삭제, 아니면 갈무리, 콜백 없으면 폴백)는 정확히 검증된다. 한계를 테스트 파일 상단에 적어뒀다.

## 정리

- **피드백은 코드와 대조한 뒤 판정한다.** 8건 중 3건이 이미 있는 기능이었다. 만들기 전에 찾아보면 중복 구현도, 발견성 문제를 기능 문제로 오진하는 것도 막는다.
- **거절 기준이 있으면 판정이 빠르다.** "블럭 위에 뭔가 얹지 않는다"는 원칙 하나로 절반이 정리됐다. 기준이 없으면 좋은 제안 하나하나에 흔들린다.
- **기존 제스처와 충돌하는 요청은 선택지를 셋으로 좁혀 묻는다.** Shift 드래그 삭제는 토스와 부딪혔고, 제일 안전한 조합(목적지가 갈무리함일 때만)으로 합의하는 데 한 줄이면 됐다.

롤백 지점: `release/pre-feedback-round-1`. 실기기 확인 대기: 라이트/다크 글로우 감각, Firefox 중클릭 자동 스크롤 억제 여부, ? 버튼으로 생성된 블럭이 화면 중앙에 오는지.
